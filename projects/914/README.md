# 1975 Porsche 914 EV Conversion

Forward-engineering project. Unlike the other vehicles under `projects/`, nothing here is
reverse-engineered: every module on the car is either my own design or open-source
hardware/software, so all CAN traffic and firmware behaviour is known **by design** rather
than discovered. The DBC is authoritative because it generates the firmware's schema header,
not because it was inferred from captures.

Most of the `canre` analysis toolkit therefore does not apply — there are no unknown IDs to
triage, no correlation sweeps to run, and no InfluxDB corpus. The rules that do apply are the
shared ones: artifacts in `artifacts/`, plans in `plans/`, no unreviewed conclusions in files.

## The vehicle in brief

Full overview lives in the hub's `914.md`.

- **Base:** 1975 Porsche 914, EV-converted ~10+ years ago by a previous owner, substantially
  re-engineered since — new inverter, new charger, custom battery + BMS, custom VCU.
- **Motor:** original Greatland Electric (~250 Nm), through the original transmission via a clutch.
- **Inverter:** Nissan Leaf Gen2 + openinverter control board, running stm32-sine 5.35 (custom build).
- **Charger:** Tesla Gen2 OBC + openinverter Tesla charger board, stm32-teslacharger v1.21.
- **Battery:** Farasis modules (Zero Motorcycle type, 28S each). Currently 84S2P, ~18 kWh,
  ~70 mi range. A third string (84S3P) is planned.
- **BMS:** custom boards, 2x LTC6813 per CellBox, IsoSPI daisy-chained. Firmware `914-control`
  + `lib-mbed-ltc681x`.
- **VCU:** LPC1768 + mbed-os + MCP23017 I2C expander. Nucleo-G474RE planned.

## Telemetry map and the DBC

`914-telemetry.dbc` is generated by `tools/generate_914_dbc.py` in the `914-control` firmware
repository, which also emits the firmware's `src/schema_id.h`. The generator is the single
source of truth; the DBC and the header are both outputs.

Conventions the DBC encodes:

- **Extended 29-bit ID** => synthetic. A value the VCU knows internally that no CAN controller
  ever saw.
- **Standard 11-bit ID** => the frame really was on the vehicle bus.
- Little-endian (Intel) throughout.

The firmware broadcasts `SCHEMA_HASH` on the wire, so a decoder holding a stale DBC reports a
hash mismatch rather than plausible wrong numbers. **This copy is a third destination for a
generated file** — regenerate it together with the firmware header and the hub's copy, never
by hand. See `tools/README.md` in `914-control`.

## Android app

The `:p914` module in `android-app/CanLoggerApps/` is a display + logger app, scoped like
`:vtrux` but with a different transport. **The logger half works on the car as of 2026-08-13;**
the display is future work.

The car has no gs_usb CAN dongle interface — the roadmap item to add one is still open. What it
has is the VCU emitting this map as **SLCAN (LAWICEL ASCII) over its USB CDC serial port**
(`0d28:0204`, "MBED CMSIS-DAP"), so the app's data source is a serial device, not a `UsbDevice`
handed to `GsUsbDevice`. The frame model and DBC parser already handled 29-bit extended IDs
unchanged.

What was built for it: `SlcanReader` and `SlcanSource` in `:cancore` (a LAWICEL reader verified
against firmware-computed CRCs), `CanFrameSource` as a three-member seam so the logging service
accepts a non-gs_usb source without the multi-dongle path being touched, and a hand-rolled
CDC-ACM reader in `:p914`. Full detail in `android-app/notes/plans/914-app.md`.

**The app also flashes the VCU** (2026-08-13). The same USB device exposes a mass-storage
interface alongside its CDC one, and that volume is the mbed's flash-by-copy route, so the phone
can write a firmware image and then reset the target with a CDC `SEND_BREAK`. Driven over adb, it
means the car can be reflashed with no laptop present — firmware and app development in one
sitting. See `android-app/notes/canlogger-build-notes.md`.

One modelling note, resolved: the single serial port carries both real 11-bit vehicle traffic and
synthetic 29-bit VCU internals, but that distinction is already carried losslessly by the ID width
and the DBC's extended marker. It is a presentation concern, not a transport one — **one bus**.

## Publish scope

This folder is published. The hub is not, and some hub content stays out permanently:

- **BMS board schematics and layout** — possible proprietary cellbox information. Not in the hub
  today either; if they ever need a home in this repo, use an excluded subfolder.
- **Archived openinverter forum threads** (HTML and extracted text) — third-party content. Link
  to the live threads instead of republishing them.
